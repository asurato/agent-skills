# 技術文書の作成・更新

このスキルは、汎用的な開発文書(markdown)を作成・修正する際に使用する。
AI特有の文章の癖を抑え、読み手に取って要点が伝わりやすい簡潔な文書作成を目的とする。

コードやコードのコメントといったmarkdown以外のファイルや、レビューのコメントは対象外とする。

## 1. タグの説明

当スキルの各ルールには、判断の強さを示す次のいずれかのタグを付ける。
ただし作成する文書の中にこれらのタグは露出されない。

- [Must]: 必ず遵守する。
- [Should]: 原則守る。適用の除外には明確な理由が必要。
- [May]: 守るかどうかは各自の判断にゆだねる。

## 2. ルール

### 2.1. 冒頭のタイトルの直後で文書の目的を簡潔に説明する [Must]

この文書の方向性を示し、読み手の理解を促進する。

### 2.2. 文書の目的の直後で、この文書では記述しない点を簡潔に説明する [Should]

どんな内容を記述しないのかを明示し、AIが際限なしに詳細な情報や補足を記載することを防ぐ。
新規に文書を作成する際は、ユーザーに何を記述し、何を記述しないかが確認されることが望ましい。

### 2.3. 章や節には番号を付ける [Must]

下記のように節や小節の番号は章や節の番号に続く形で付与する。

```
## 1. 章タイトル
### 1.1. 節タイトル
#### 1.1.1. 小節タイトル
```

### 2.4. 章の構成では序論→本論→結論という流れを意識する [Should]

章の構成では、序論、本論、結論の流れを意識して構成する。
ただし、序論や本論といった言葉を見出しに取り入れる必要はない。

```
## 1. 概要
## 2. 背景
## 3. 課題
## 4. 実装計画
## 5. 結論
```

### 2.5. 概要の章を冒頭に設ける [May]

文書が長くなる場合は、概要の章を冒頭に設ける。
文書全体が短い場合は、省略しても構わない。

### 2.6. 章の構成は文書の作成前に合意を取る [Must]

文書を作成する前に、章の構成を最初に決定する。
章構成の初稿や章構成に大幅な変更が入った場合は、**ユーザーの確認を得てから**中身を作成する。
逆に細かい章構成の修正ではユーザーへの確認は不要である。

ユーザーの確認を得る時は、章や節の内容を1行にまとめ、合わせて説明する。
ただし、章の数が多すぎたり「背景」や「結論」などほぼ自明だったりした場合は適宜省略する。
以下はあくまで一例である。
```
## 1. 背景
## 2. 計画
### 2.1. 計画A
Aについての説明
### 2.2. 計画B
Bについての説明
### 3. 評価
評価手法を述べる
```

### 2.7 章の構成はストーリーの流れを意識する [May]

章の流れは、序論→本論→結論という流れを汲むこと。
ただし文章量が少ない場合や文書の方向性として不自然になる場合は、その限りではない。

### 2.8. 箇条書きは項目の粒度を揃える [Should]

項目の粒度が揃わない箇条書きは、箇条書きで表現されるべきではない可能性が高い。
項目の粒度を揃えるように見直し、難しい場合は見出しの追加による分割も検討すること。

### 2.9. 親子関係のある箇条書きを採用する [Should]

文章の圧縮形式として優れているため、積極的に活用すること。

### 2.10. 既存の文章を変更するときに部分的な変更に閉じない [Must]

後から文章の編集を指示した時に、単なる追記で完了されるケースが多い。
その結果、局所的に文章が増加してアンバランスな文章に鳴ったり、文章の流れが不自然になりがちになる。
必要に応じて、文章構成の変更も検討する。

### 2.11. 全ての説明を文章に頼らない [Should]

文章だけで説明するのではなく、箇条書きや表を用いた説明を心がける。
ただし、カラムが2つしかない表は別の表現形式を模索すること。
